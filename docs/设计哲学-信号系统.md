# 信号系统设计文档

> 2026-05-19

---

## 一、概述

dscode 的信号系统是一个端到端的反馈回路：每次工具调用后采集信号，通过拉普拉斯平滑合并为单一信念度，根据信念度阈值自动向 LLM 注入提示词或中止任务。系统由三个独立组件构成，一个决策入口：

```
工具执行完毕
     │
SignalCollector.collect(name, output, exit_code, content)
     │
     ├── ToolFailed — 确定性错误
     ├── ToolError  — 启发式错误
     └── EditLoop   — 序列模式错误
     │
     ▼
BeliefTracker.observe(signals)
     │  α = 3 + Σsuccess, β = 1 + Σfailure
     │  B = α/(α+β)
     │
     ▼
DecisionEngine.decide(B, errors)
     ├── B ≥ 0.70 → None
     ├── B < 0.70 → Inject（写入对话存储）
     └── B < 0.30 → Abort（中断本轮）
```

## 二、信号采集

### 2.1 设计原则

信号采集只有一个入口 `SignalCollector.collect()`。所有信号都在同一个方法中产生，`turn.rs` 只负责调用它并传递参数，不进行任何额外的内联信号检测。这样做保证了：

- 信号来源可追溯、可测试
- 新增信号类型只需修改 `collect()` 和 `SignalKind`
- 信号采集逻辑不与执行流程耦合

### 2.2 信号类型

系统定义三类信号，覆盖工具调用的三个维度：

| 信号 | 来源 | 检测方式 | 确定性 | 权重 |
|------|------|---------|--------|:---:|
| **ToolFailed** | 工具执行结果 | `exit_code ≠ 0`（Bash）或输出以 `"Error:"` 开头（其他工具） | ✅ 确定性 | 1.0 |
| **ToolError** | 工具输出文本 | regex 匹配 `error[E\d+]:`、`FAILED`、`Permission denied`、`Timeout` 等 | ❌ 启发式 | 0.3~0.9 |
| **EditLoop** | 工具调用序列 | W=6 窗口内 Edit > 4，或 Edit↔Diff 交替且无 Bash/Grep/Read | ✅ 确定性 | 0.4~0.9 |

#### ToolFailed

确定性工具错误。两条检测路径：

- **Bash 工具**：`bash::execute()` 通过 `child.status.code()` 获取进程退出码，不为 0 时产生 `ToolFailed`。退出码信息通过 `ToolExec` trait 的返回值（`Option<i32>`）一路透传到 `SignalCollector`，不经过输出文本分析。
- **其他工具**（Read/Write/Edit/Glob/Grep/WebSearch/WebFetch）：Rust 函数直接执行，没有进程退出码。失败时 `Result::Err` 被 `execute_one_sync` 统一格式化为 `"Error: tool execution failed: ..."` 前缀的字符串。`collect()` 通过 `full_content.starts_with("Error:")` 捕获。

权重统一为 1.0——工具真失败了就是铁的事实，不按错误类型区分。

#### ToolError

启发式错误检测。基于预编译的 regex 模式库（`OnceLock` 全局静态，只编译一次）：

| 模式 | 权重 | 说明 |
|------|:---:|------|
| `error[E\d+]:` | 0.9 | Rust 编译错误 |
| `error: aborting due to \d+ previous error` | 0.9 | Rust 批量错误 |
| `FAILED ...::...` | 0.8 | 测试失败 |
| `FAILURES===` | 0.8 | Pytest 失败 |
| `Traceback (most recent call last):` | 0.8 | Python 异常 |
| `Permission denied` / `EACCES` | 0.5 | 权限拒绝 |
| `command not found` / `No such file` / `does not exist` | 0.5 | 找不到 |
| `Timed? ?out` / `timeout` / `killed` | 0.3 | 超时 |

正则匹配不是确定性的——输出文本中可能出现 "error" 但不代表命令失败了。因此权重低于 ToolFailed。

#### EditLoop

序列模式检测，用于捕获"盲写"循环。维护一个滑动窗口存储最近 W=6 次工具调用名称。触发条件：

| 条件 | 严重度 | 含义 |
|------|:-----:|------|
| Edit 调用次数 = 5 | 0.6 | 窗口内绝大部分是编辑 |
| Edit 调用次数 = 6 | 0.8 | 几乎全是编辑 |
| Edit 调用次数 > 6 | 0.9 | 防御值，不可能超窗口 |
| Edit↔Diff 交替 1 次 | 0.4 | 编辑-对比-编辑的早期循环 |
| Edit↔Diff 交替 2 次 | 0.7 | 编辑-对比循环已建立 |
| Edit↔Diff 交替 ≥ 3 次 | 0.9 | 严重的盲写循环 |

Edit↔Diff 交替检测还要求窗口内完全无 Bash/Grep/Read 操作——如果有读操作，说明 agent 至少尝试理解代码，不是纯盲写。

`SignalCollector` 自维护 `call_history: VecDeque<String>`，跨多次工具调用追踪序列。每次 `collect()` 调用时 push 当前工具名，超限时 pop 最旧。

## 三、信念度计算

### 3.1 从信号到观测

一次工具调用可能同时产生多个信号（如 Bash 既非零退出又在输出中匹配到 Rust 编译错误）。多个信号合并为一条观测，合并规则是 **取 max(severity)**，不叠加：

```
signals = [ToolFailed(0.9), ToolError(0.5)]
  → total_failure = max(0.9, 0.5) = 0.9
  → success_weight = 1.0 - 0.9 = 0.1
  → failure_weight = 0.9
```

举例：

| 工具调用 | 信号 | Observation |
|---------|------|:----------:|
| `Read(path)` | 无 | {1.0, 0} |
| `Bash(cargo build)` | ToolFailed(0.9) + ToolError(0.8) | {0.1, 0.9} |
| `Edit(path)` | EditLoop(0.9) | {0.1, 0.9} |
| `Bash(make test)` | ToolError(0.5) | {0.5, 0.5} |

不叠加的原因：NonZeroExit 和 ToolError 通常报告同一件事（编译失败既有 exit code 1 又有 error[E0308]），叠加会重复计数。

### 3.2 拉普拉斯平滑

贝叶斯更新公式：

```
α = α_先验 + Σ 窗口内 success_weight
β = β_先验 + Σ 窗口内 failure_weight

B = α / (α + β)
```

先验值当前为 α=3, β=1，对应初始 B=0.75。这是"信任先验"——因为使用这个模型本身就意味着信任它能正确使用工具。先验只在窗口刚填满时影响信念，长期被真实观测淹没。

### 3.3 滑动窗口

BeliefTracker 维护 `VecDeque<Observation>`，默认 W=16。每次 `observe()` 调用：

1. `Observation::from_signals(signals)` 将信号合并为一条观测
2. 窗口满时 `pop_front()` 最旧观测，从 α/β 中减去对应权值
3. Push 新观测，α += success_weight，β += failure_weight
4. 记录错误详情到 `recent_errors`（供注入使用）

窗口语义：新用户输入时清空窗口（`reset()`），信念回到 0.75。不可配置（当前硬编码）。

### 3.4 滑动计算示例

```
W = 4, α_先验 = 3, β_先验 = 1

调用1: Read → 无信号 → 窗口 [{1.0,0}]              α=4.0 β=1.0 B=0.800
调用2: Bash(ToolFailed 0.9) → 窗口 [{1.0,0},{0.1,0.9}] α=4.1 β=1.9 B=0.683
调用3: Bash(ToolFailed 0.9, ToolError 0.5 → max=0.9)
  → 窗口 [{1.0,0},{0.1,0.9},{0.1,0.9}]               α=4.2 β=2.8 B=0.600
调用4: Read → 无信号 → 窗口 [{1.0,0},{0.1,0.9},{0.1,0.9},{1.0,0}] α=5.2 β=2.8 B=0.650
调用5: Grep → 无信号（窗口满，调用1被挤出）
  → 窗口 [{0.1,0.9},{0.1,0.9},{1.0,0},{1.0,0}]       α=5.2 β=1.8 B=0.743
```

信念的变化呈现自然恢复曲线：旧错误被新成功观测挤出窗口后，B 逐步回升。

## 四、决策与干预

### 4.1 决策阈值

DecisionEngine 基于当前信念度 B 和错误列表输出三种决策：

```
B < 0.30 ─→ Abort（直接中断本轮，返回 Failed）
0.30 ≤ B < 0.50 → Inject(警告)
0.50 ≤ B < 0.70 → Inject(提醒)
B ≥ 0.70 ─→ None（不干预）
```

默认阈值根据拉普拉斯贝叶斯的物理含义选取：

| 基准值 | 含义 |
|:-----:|------|
| 0.30 | 5 次连续严重错误后 ≈ 0.33 — 严重失真的下限 |
| 0.50 | 2 次严重错误 + 1 次轻微 ≈ 0.50 — "好坏参半"的分界线 |
| 0.70 | 初始 B=0.75，1 次错误后 ≈ 0.63 — "基本顺利"的下界 |

阈值可由 `DecisionEngine::with_thresholds(abort, warn, remind)` 配置。

### 4.2 注入位置

注入时机在同一次 `turn.rs::execute()` 循环内，工具执行完成后、下一轮 LLM 调用之前：

```
Phase 3: 工具执行 → SignalCollector.collect() → belief.observe()
Phase 4: stop = "tool_use"
  ├─ DecisionEngine.decide(B, errors)
  │   ├─ Inject → store.add_user(msg)
  │   └─ Abort  → return Failed
  └─ messages = store.lines() → 下一轮 LLM
```

注入消息作为一条独立的 User 消息写入对话存储（`store.add_user()`），不在 system prompt 中注入（保护前缀缓存），不追加到用户输入末尾。

### 4.3 注入内容

注入包含具体错误信息：

```
[System note: Multiple failures detected (belief 0.37). Adjust approach.
Recent errors:
- Bash(cargo build): Rust compilation error (error[E0308])
- Bash(cargo build): process exited with code 1]
```

三个级别的注入内容：

| 级别 | B 范围 | 错误条数 | 格式 |
|------|:------:|:-------:|------|
| Reminder | 0.50~0.70 | 最近 3 条 | `[System note: Some tool executions showed issues...]` |
| Warning | 0.30~0.50 | 最近 5 条 | `[System note: Multiple failures detected...]` |
| Abort | < 0.30 | — | `TurnDecision::Failed("aborted by DecisionEngine")` |

## 五、信号链路完整路径

```
┌─ 工具执行 (tools/runner.rs) ───────────────────────────────┐
│ bash: Result<(String, Option<i32>)>                        │
│ 其他: Result<(String, bool, String, Option<i32>)>, exit=None│
│ 错误时: "Error: tool execution failed: ..."                │
└──────────────────────┬──────────────────────────────────────┘
                       │
┌─ turn.rs Phase 3 ────▼──────────────────────────────────────┐
│ ToolRunResult { content, exit_code, ... }                  │
│                                                             │
│ signal_collector.collect(&name, &output, exit_code, &content)│
│   ├─ exit_code != 0 → ToolFailed                           │
│   ├─ content starts_with "Error:" → ToolFailed              │
│   ├─ detect_error(regex) → ToolError                       │
│   ├─ push history → detect_edit_loop → EditLoop             │
│   └─ Vec<Signal>                                           │
│                                                             │
│ belief.observe(&result.signals)                             │
│   ├─ Observation::from_signals(signals) → max(severity)    │
│   ├─ window.push(obs), window.full → pop_front()            │
│   ├─ α += success_weight, β += failure_weight               │
│   └─ recent_errors.push(detail)  (if ToolFailed|ToolError)  │
│                                                             │
│ 标题栏实时更新 belief()                                      │
└──────────────────────┬──────────────────────────────────────┘
                       │
┌─ Phase 4: stop="tool_use" ──▼──────────────────────────────┐
│ DecisionEngine.decide(belief(), &recent_errors)              │
│   ├─ None     → 不干预                                     │
│   ├─ Inject   → store.add_user("[System note: ...]")        │
│   └─ Abort    → return Failed("aborted by DecisionEngine")  │
│                                                             │
│ messages = store.lines()  (含注入消息)                      │
└──────────────────────┬──────────────────────────────────────┘
                       │
┌─ 下一轮 LLM ────────▼──────────────────────────────────────┐
│ LLM 收到:                                                  │
│   [User] fix the tests                                     │
│   [Assistant] tool_calls(A, B)                             │
│   [User] result_A, result_B                                │
│   [User] [System note: Multiple failures detected...]      │
│   → LLM 调整策略                                            │
└────────────────────────────────────────────────────────────┘
```

## 六、边界情况

### 6.1 exit_code = 0

Bash 命令成功退出（code 0）不产生 `ToolFailed` 信号。`collect()` 中只有当 `exit_code != 0` 时才 push 信号。

### 6.2 同时匹配多条 regex

`detect_error()` 按优先级顺序匹配。一旦匹配到第一条即返回，不继续匹配后续模式。优先级按编译/测试/权限/超时递减。

### 6.3 窗口未满时不检测 EditLoop

`detect_edit_loop()` 要求 `history.len() >= seq_window`（6 次）才检测。前 5 次工具调用不产生 EditLoop 信号。

### 6.4 注入空错误列表

当 `recent_errors` 为空时，注入内容不包含 `Recent errors:` 段落，只显示 `[System note: Some tool executions showed issues (belief X.XX).]`。这可能是初始状态或错误已过期。

## 七、组件文件与接口

| 组件 | 文件 | 公开方法 | 外部依赖 |
|------|------|---------|---------|
| SignalCollector | `guard/collector.rs` | `new()`, `collect()` | 0 |
| BeliefTracker | `agent/belief.rs` | `new()`, `observe()`, `belief()`, `reset()` | 0（依赖 Signal 类型） |
| DecisionEngine | `agent/decision.rs` | `new()`, `decide()` | 0 |

三个组件均零外部依赖（仅 DecisionEngine 依赖 Signal 类型定义）。可以独立测试、独立修改、独立替换。
