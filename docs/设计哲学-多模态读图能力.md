# 设计哲学：多模态读图能力

> 更新日期：2026-09-03

编程 Agent 常需要查看截图、图表、面板一类的视觉内容。多模态读图能力让 `Read` 捕获的图片能以正确、可预期、可负担的形式送达视觉模型。本文记录这一能力的设计取向与行为边界；协议与字段的逐条规格见代码与 `docs/tools.md`。

---

## 1. 设计目标

- **能力可声明**：会话启动时即确定当前模型是否支持图片、支持哪些格式与限额，冻结为会话事实；模型切换时做兼容性校验，不兼容则拒绝。
- **引用而非搬运**：conversation 只保存图片的确定性引用（`image://sha256:<hex64>`），像素本体在内容寻址缓存里；历史消息不含 base64 大段数据。
- **单次消费**：一张图只在模型第一次看到它时被物化成像素，之后降级为稳定的文本引用。
- **预算可预期**：数量、字节、边长、像素限额明确；超限时要么失败，要么按既定规则降级。
- **能力关闭时行为不变**：文本会话的 Read、工具面、prompt 与旧版完全一致；`image://` 在无能力会话里是未知 scheme，fail closed。

---

## 2. 能力模型：会话怎么知道模型能看图

能力在 **session 初始化时解析并冻结**，持久化到 `model-capabilities.json`；恢复时重算指纹核对，漂移即拒绝启动。

- **能力声明来源**（分辨率从高到低）：显式配置 `image_input` > backend 的 `image_input_capability(model)` 声明 > 默认 `Unsupported`。
- 能力包含：支持/不支持的枚举（`Unsupported` / `OpenAiChatImageUrl`）、允许的 MIME 集合、wire 协议、token 估算器、以及数量/字节/边长/像素限额；这些字段共同构成**能力指纹**。
- **模型切换门控**：不支持图片的会话接受任意模型但永远 text-only；图片会话要求指纹精确匹配，切换不兼容模型时拒绝启动/切换——防止"这个模型其实不认 data URL"这类静默失效。

一句话：能力是会话的**静态事实**，不是请求时的临时假设。

---

## 3. 读图流程（概念模型）

一次"看图"经历四个阶段，每一阶段都有明确的所有者与失败语义：

```
Read 捕获 → 内容寻址缓存（不可变对象）→ conversation 只存引用 → 请求时物化
```

1. **捕获**：`Read` 对本地文件做 magic 嗅探（PNG/JPEG/GIF/WebP），单图做大写 MIME 双重校验（Mink 支持集 ∩ 模型 allowed_mime）与字节/边长/像素限额；不合法直接失败，不产生半成品。
2. **缓存**：原始字节写入 `<home>/.mink/cache/images/v1/`，以 SHA-256 命名（内容寻址、天然去重、不可变）；两阶段提交 + 读回校验，无索引文件；`image://` 的 id 就是哈希。
3. **引用**：工具结果携带 `tool_attachment` 块——只有引用、预算元数据（格式/尺寸/字节）与工具调用关联，**没有路径、没有文件名**（路径只在当时工具结果里出现，防止仓库路径泄漏进历史）。
4. **物化**：请求发送前，把本轮的未消费引用展开为 OpenAI `image_url` data-URL（原始字节 base64，不做转换、不生成变体）；已消费的历史引用则投影为确定性文本。

---

## 4. 单次消费生命周期

这是本能力的关键取舍。规则按"最后一条 assistant 消息"划分：

- **未消费批**：位于最后一条 assistant 消息**之后**的引用——模型还没看过这些图，本次请求把它们物化为像素，用后即"消费"。
- **已消费引用**：位于其**之前**的引用——投影为 `[Previously attached image: image://... (WxH format)...]` 文本，模型可用 `Read image://...` 重新注入，幂等。

**为什么这样设计**：

- 像素只发送一次 → 视觉 token 成本可预测，历史引用不再产生重复费用；
- 引用的**消费状态只由时序决定**，不需要额外持久化状态；崩溃后重发一次也安全（方向是"多猜未消费"，宁可重发一次也不静态丢失）；
- 模型仍然拥有"再看一次"的手段（`Read image://`），信息没有丢，只是换成了按需加载。

---

## 5. 配额与预算：三层防线

| 层 | 限额（默认） | 超限行为 |
|---|---|---|
| 单图捕获 | 字节/边长/像素上限（可配） | 工具失败，不产生引用 |
| 单请求批 | 600 张 / 16MB 原始字节（可配） | 本轮的图**失败**；历史引用降级 `[image unavailable]` |
| 请求体 | 32MB 硬上限 | 请求失败 |

关键设计：**每批配额从 0 计数、批次之间重置**。这样历史引用永远不会被锁死——哪怕旧图很多，也不影响本轮新图；超限只影响"这一次"，不污染持久化状态，也不改写历史。

压缩器与主请求共用同一投影：已消费图片在压缩估算里只算文本引用，不会因为"历史上看过图"而触发虚假的上下文压力。

---

## 6. 降级矩阵（行为表）

| 场景 | 行为 |
|---|---|
| 能力关闭的会话 | 与旧版逐字节一致；`image://` 是未知 scheme，fail closed |
| 本轮新图物化失败（缓存缺失/校验失败/超配额） | **本次请求失败**——Read 已经声称成功，不能对模型谎报"已附加" |
| 历史引用物化失败 | 降级 `[image unavailable: ...]` 文本 + 每 id 一次性提示；模型可重试 |
| MIME 不在模型允许集 | 捕获即失败 |
| 模型切换后能力不兼容 | 拒绝切换/启动 |
| 子代理 fork 后引用父缓存 | 父引用按历史 unavailable 处理（子代理不继承缓存） |

原则：**本轮失败诚实失败，历史问题可解释降级**；任何情况下都不改写 conversation 历史。

---

## 7. 与系统其他部分的关系

- **上下文压缩**：摘要输入降噪把 `tool_attachment` 置为占位；compress 后的 checkpoint 投影与主请求共用同一套消费状态，视觉 token 不会重复计。
- **子代理**：不继承父图片缓存；fork 进来的父图像引用按 unavailable 降级——隔离优先，避免子代理悄悄复用父会话的图片资源。
- **VFS**：只读 VFS 的 Read 可以逐张返回图片（字节不跨批累积），虚拟路径不走本地缓存。
- **终端**：超长工具结果折叠后仍显示首个 `artifact://ID`；图片不会出现在 TUI 的正文渲染里（模型侧消费）。

---

## 8. 取舍：为什么不是别的方案

- **为什么内容寻址缓存而不是复制进 session**：同一张图（如重复截图）只存一份；哈希 id 自证身份，恢复无索引可依赖。
- **为什么不用路径/文件名引用**：路径是可泄漏的仓库事实，且文件可能被移动/删除；引用必须只依赖内容本身。
- **为什么不做解码重编码/缩放变体**：转换可能引入信息损失、依赖图像处理全家桶；"原字节直通"是行为最可预测、数据最保真的选择，token 估算已在模型侧近似处理。
- **为什么缓存 home-scoped**：图片属于用户机器而非某个会话；子代理不继承是成本与隐私的显式取舍。
- **为什么能力关闭时静默**：多模态是本项目的增量能力，关闭路径必须与既有文本工作流字节兼容，避免"升级后行为神秘变化"。

---

## 9. 限制与未来演进

- **当前只覆盖本地文件捕获**；远程图片 URL 直通属于后续设计，尚未实现。
- token 估算是**近似**（OpenAI 分块模型 + 模型侧 detail 档位），用于预算判断而非计费口径。
- 单次消费的"安全方向"：时序不定时宁可多发送一次，不会因为崩溃少发而让模型丢失画面。
- 若未来模型支持多会话缓存或不同 wire 协议，`ImageInputCapability` 的协议枚举与 token 估算器字段已预留扩展点；新增协议必须走能力指纹与降级矩阵，不允许隐式转换。
